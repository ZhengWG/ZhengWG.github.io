Model the encoder, prefill, and decode separately, account for the transfer cost of embeddings and the KV cache, and derive machine ratios and admission control from the target SLO.

KV cache transfer: schemes and latency

Scenario Scheme Key points
TP_p = TP_d (homogeneous) direct rank-i → rank-i transfer layouts align, and SGLang bypasses staging automatically
TP_p ≠ TP_d (heterogeneous) per-worker gather+permute → staging buffer → bulk RDMA → scatter on the peer the head dimension is merged/split by a routing table; the token dimension removes block fragmentation; 2-5× faster than per-token slices; never centralize on rank0 (that uses only 1 NIC)
MLA direct transfer, no staging the latent is shared by all heads, so the head dimension is immune (token-dimension fragmentation remains)
Destination blocks in place D preallocates the block_table and preregisters the pool, and P lands data directly with RDMA writes at offsets multiple P ranks write concurrently to different offsets of the same D buffer → the concat is eliminated

① layer-wise: send layer i as soon as it is computed, overlapping with later layers; actual exposure depends on the pipeline and the link
② Sample the first token on the P side: less waiting, but TTFT may still include the last segment of KV transfer
③ GPUDirect + NIC affinity binding: avoids the CPU bounce (effective bandwidth 8→20GB/s)

  • Over RDMA, only 0.7–6.5% of the transfer is exposed; over TCP it adds 7–33%. With long inputs, most of the TCP transfer overlaps with chunked prefill compute (about 2.6 s/rank in theory at 32K, of which only 0.63 s is exposed); with short inputs it is almost fully exposed.
  • The first decode step (the interval to the second token) is 12–15 ms in all three setups and does not get longer from waiting on KV; TTFT still includes the transfer of the last segment of KV.
  • Mismatched TP (P TP4 → D TP2): without staging it is 10–52% slower than homogeneous TP4→TP4; with SGLANG_DISAGG_STAGING_BUFFER=1 it is only 1.4–6% slower.
  • Affinity: Mooncake GPU→GPU writes over a single NIC reach 48.9 GB/s, halving to 24 GB/s when the GPU is paired with a NIC across NUMA nodes.

Whether to disaggregate also depends on decode jitter when a long prefill is inserted. Measured (16 concurrent decode streams, with one 16K prefill inserted every 6 seconds): colocated on the same GPUs, the decode ITL P99/P50 is 27× (default chunk), 48× (mixed-chunk 2048), and 13× (mixed-chunk 512, but whenever a chunk is running every decode step takes about 180 ms, and the 16K prefill is also 9% slower); with PD it is 1.23× (P99 17.4 ms). Here a smaller chunk lowered the worst-case stall, but there is still a trade-off between decode latency and prefill efficiency; PD isolates the two kinds of workload on separate resources.

Heterogeneous KV, prefix reuse, and hierarchical caching

A single unified KV pool allocated as “the same size per layer per token” cannot adequately represent hybrid attention. Distinguish by type — variable-length KV, recurrent state, sliding windows, compressed blocks, and the uncompressed tail — and include the type, position, head/TP ownership, and destination offset in the transfer metadata.

Object Allocation and reuse principle
Standard KV paged block management; prefixes are reused by token/position and model version
GDN recurrent state only saved prefix checkpoints can be restored; an arbitrary historical state cannot be truncated out of the final state
CSA/HCA compressed KV record both the completed compressed blocks and the incomplete tail, and preserve the compression boundary at handoff
SWA / indexer maintain the sliding-window lifetime and the index data separately; moving only the latent does not make the state complete

The benefit of prefix caching depends on whether the complete state can be restored; it does not simply multiply out to a fixed 1/4 from “15/60 layers”. Hierarchical caching extends capacity through GPU → CPU → NVMe; whether to read back is decided by lookup + queueing + transfer + layout restoration < time to recompute the prefix, including contention for bandwidth with online requests. Long contexts are usually more worth reusing, but small requests may not be worth the extra hop.

SLO-driven resource ratios and admission control

The goal is to maximize the throughput that meets percentile SLOs on TTFT/ITL. First pin down the percentile and the measurement window, then sweep batch, context, and load; average TPOT cannot stand in for P99 ITL.

1
2
3

TTFT = queueing + encoder + prefill + exposed KV transfer + first-token output
n_P : n_D = (avg input tokens / prefill tok/s per P instance)
          : (avg output tokens / decode tok/s per D instance)

These throughputs must be measured under the target SLO and the real length distribution; cache hits are credited by the prefill work they actually save. The input and output length distributions directly change the required ratio. Routing first excludes instances whose memory or predicted tail latency would exceed the limits, then weighs prefix hits, queue length, KV occupancy, and SLO headroom; real-time, interactive, and batch workloads can be served from separate pools.

In this PD comparison, colocation uses 2 GPUs and disaggregation uses 2P+2D GPUs; P99/P50 drops from 13–48 to about 1.2. The two setups use different resources, so the comparison is mainly for observing how long prefills affect decode jitter.

Ratio = match the throughput of each stage: n_E : n_P : n_D = (load/Thr_E) : (load/Thr_P) : (load/Thr_D)
   Thr_X = throughput of a single instance under the SLO (images/s, prefill tok/s, decode tok/s), not per-request latency
   D batches hundreds of requests at once; using per-request latency ratios directly (e.g. E=1.04s / P=1.93s / D=8s) overestimates D by an order of magnitude

Four principles for the communication mechanism (so that the benefit of the ratio is actually realized):
① Async + queue decoupling: E→P goes through a request queue, not a synchronous RPC (otherwise E's jitter propagates directly into bubbles in P)
② Preregister transfer resources: IPC slabs / RDMA MRs registered at startup, zero setup at runtime
③ Decouple batch boundaries: E batches by image and P batches by token, regrouped at the queue, so neither has to accommodate the other
④ Backpressure: use queue depth for admission control, so E cannot run ahead and flood P's GPU memory
