Introduction

Design patterns can be seen as the programming ideas of object-oriented programming, and design principles are the guiding outline for those ideas. SOLID is an acronym for the five basic principles of object-oriented design (OOD): S - Single Responsibility Principle; O - Open-Closed Principle; L - Liskov Substitution Principle; I - Interface Segregation Principle; D - Dependency Inversion Principle

SOLID Principles

Single Responsibility Principle

A class should have one, and only one, reason to change . In plain words: a class is responsible for only one function, or one group of similar functions. The following code for animal behavior clearly violates the single responsibility principle: if other scenarios need to be added, the runnning method must be modified, which creates risks for the existing logic:

Open-Closed Principle

OCP (Open Close Principle): software entities (such as classes, modules, and functions) should be open for extension but closed for modification . That is, when designing code you need to consider later changes: when adding a function, modify the original code as little as possible, and when modifying a module, do not affect other modules. For example, add an interface for observing animals on top of the animals above. Liskov Substitution Principle

LSP (Liskov Substitution Principle): everywhere a base class can be referenced, a subclass must be usable transparently . That is, wherever a parent class can appear, a subclass can replace it and provide the same functionality, but not the other way around. Below, a subclass of terrestrial animals is created: the monkey. Dependency Inversion Principle

DIP (Dependency Inversion Principle): high-level modules should not depend on low-level modules; both should depend on abstractions. Abstractions should not depend on details; details should depend on abstractions. That is, classes with the same or similar functionality need to be abstracted into an interface or abstract class, and the concrete implementation classes inherit from that abstract class. Suppose an interface for eating needs to be added to the animals above. A simple design is as follows. The problem is that food is not isolated from animals, so it becomes hard to modify the code when scenarios such as adding a food type arise.

from abc import ABCMeta, abstractmethod


class Animal(metaclass=ABCMeta):
    def __init__(self, name):
        self._name = name

    def eat(self, food):
        if self.check_food(food):
            print(self._name + "eat" + food.get_name())
        else:
            print(self._name + "doesn't eat" + food.get_name())

    @abstractmethod
    def check_food(self, food):
        """检查食物是否能吃"""
        pass


class Food(metaclass=ABCMeta):
    def __init__(self, name):
        self._name = name

    def get_name(self):
        return self._name

    @abstractmethod
    def category(self):
        """食物类别"""
        pass


class Dog(Animal):
    def __init__(self):
        super().__init__("Dog")

    def check_food(self, food):
        return food.category() == "Meat"

Interface Segregation Principle

ISP (Interface Segregation Principle): clients should not depend on interfaces they do not need. Use multiple fine-grained interfaces instead of one complex interface made of many methods, with each interface serving one submodule. That is, make interfaces as fine-grained as possible, with interface methods as small as possible (in moderation). from abc import ABCMeta, abstractmethod


class Animal(metaclass=ABCMeta):
    def __init__(self, name):
        self._name = name

    def get_name(self):
        return self._name

    @abstractmethod
    def feature(self):
        pass

    @abstractmethod
    def moving(self):
        pass


class IRunnable(metaclass=ABCMeta):
    """奔跑接口"""
    @abstractmethod
    def running(self):
        pass


class IFlyable(metaclass=ABCMeta):
    """飞行接口"""
    @abstractmethod
    def flying(self):
        pass


class INataable(metaclass=ABCMeta):
    """游泳接口"""
    @abstractmethod
    def swimming(self):
        pass


class MammalAnimal(Animal, IRunable):
    """哺乳动物"""
    def __init__(self, name):
        super().__init__(name)

    def feature(self):
        print(self._name + "的生理特征：恒温，胎生，哺乳。")

    def running(self):
        print("在陆上跑")

    def moving(self):
        print(self._name + "的活动方式：", end="")
        self.running()


class Bat(MammalAnimal, IFlyable):
    """蝙蝠：哺乳动物，但是不会走，会飞"""
    def __init__(self, name):
        super().__init__(name)

    def running(self):
        print("行走功能已经退化")

    def flying(self):
        print("在天空飞...", end="")

    def moving(self):
        print(self._name, "的活动方式：", end="")
        self.flying()
        self.runing()

Other Principles

LoD Principle

Each logical unit should know as little as possible about other logical units; in other words, it should only be close to its current object. Talk only to your immediate friends, and "don't talk to strangers" . This principle is also called the Law of Demeter. Typical scenario: class A holds an object of class B, and class B in turn holds an object of C. Now A needs to access an attribute of C, which is written as follows:

2
3
4

# 不合理写法
a.get_B().get_C().get_properties()
# 合理写法
a.get_C_properties()

KISS Principle

Keep It Simple and Stupid . Code should be designed to be as decoupled as possible; do not over-design, and keep the code simple and easy to understand.

DRY Principle

Don't repeat yourself . When the same problem is encountered many times, extract a common solution to improve code reuse. Ways to implement it:

  • Function-level encapsulation
  • Class-level abstraction
  • Generic design

YAGBI Principle

You aren't gonna need it, don't implement something until it is necessary. Only consider and design the functions that are necessary, and avoid over-design.

Rule Of Three Principle

Rule of Three: abstract a function only when it appears for the third time. That is, the first time you implement it, just do it boldly; the second time, although you dislike it, you still do it; the third time, you should examine the repeated/similar code and abstract it, wrapping it into a general interface. Purpose: save effort, discover patterns step by step, and prevent excessive redundancy.

CQS Principle

Command-Query Separation . A query returns a value in response to a question, while a command is a method that changes the state of an object. The two should be separated as much as possible, which helps improve system performance and also helps strengthen system security.
