HBM generations compared:

  • HBM2e: spec 3.6Gbps, 910B actually runs at 3.2 → 0.40TB/s per stack × 4 stacks = 64GB · 1.6TB/s
  • HBM3: spec 6.4Gbps, H100/H800 actually run at 5.2 → 0.67 per stack × 5 stacks = 80GB · 3.35TB/s (the public H20-96GB spec is 96GB, 4.0TB/s, which can be used to compare capacity and bandwidth at different stack counts)
  • HBM3e: spec 8–9.6Gbps; working back from the H200’s public capacity and bandwidth, the data rate per stack is about 6.25 → 0.80 per stack × 6 stacks = 141GB · 4.8TB/s B200 pushes it to 7.8 → 1.0 per stack × 8 stacks = 192GB · 8.0TB/s B300 at the same rate, switched to 12-high die stacks → 288GB · 8.0TB/s (bandwidth unchanged)
  • HBM4: interface width doubles from 1024→2048-bit, Rubin generation, ~2TB/s class per stack

Notes:

Capacity, bandwidth, and compute throughput should be compared separately. Taking public specs as an example, the H20-96GB has 96GB of GPU memory and 4.0TB/s of bandwidth, and the H200 has 141GB and 4.8TB/s; more capacity does not mean the peak of every compute path changes in the same proportion. B200→B300 only adds die layers: capacity +50%, bandwidth unchanged → the ridge point is unchanged; it exists purely for the KV pool / large models

NPU deployments should still be diagnosed separately for compute, memory access, and kernel launch: matrix operations go to the Cube, while fragmented vector/scalar operations can limit the pipeline; graph mode reduces host-side launches, and fusion reduces intermediate tensors and fragmented operations, but it cannot turn arbitrary Vector operations into Cube operations. HCCS within a node and RoCE across nodes must be modeled separately, and with 8-card nodes, EP16 already crosses nodes; confirm the actual topology and available links first, then choose the collective communication algorithm, and do not carry over the fixed 7× speedup from the simulated table.
