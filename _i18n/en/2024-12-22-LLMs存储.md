## Storage Technologies

### Multi-Level Storage

![image-20241224222350840](https://cdn.jsdelivr.net/gh/ZhengWG/Imgs_blog//2024-12-22-LLMs%25E5%25AD%2598%25E5%2582%25A8/image-20241224222350840.png){: .img-mid }

To improve execution efficiency and reduce the interaction between the CPU and memory (which hurts CPU efficiency), modern CPUs generally integrate a multi-level cache architecture. The common one is a three-level structure: L1 Cache, L2 Cache, and L3 Cache. The lower the cache level, the closer it is to the CPU, which also means it is faster, but its capacity is correspondingly smaller:

+ Ordering of storage capacity: memory > L3 > L2 > L1 > registers.

- Ordering of storage speed: registers > L1 > L2 > L3 > memory.

  | From the CPU to  | CPU cycles          | Execution time (ns) |
  | -------- | ---------------- | -------------- |
  | Registers   | 1 cycles         |                |
  | L1 Cache | ～3-4 cycles     | ～0.5-1        |
  | L2 Cache | ～10-20 cycles   | ～3-7          |
  | L3 Cache | ～40-45 cycles   | ～15           |
  | Cross-socket transfer |                  | ～20           |
  | Memory     | ～120-240 cycles | ～60-120       |

The multi-level cache design is based on the `principle of locality`:

+ **Temporal locality**: if a data item is accessed, it is likely to be accessed again soon.
+ **Spatial locality**: if a data item is accessed, data items at adjacent addresses are likely to be accessed soon too.

A hierarchical storage system consists of different levels. Data can only be copied between two adjacent levels. The upper level has smaller capacity and higher speed, and its manufacturing cost is higher.

### Cache Storage

The cache is an intermediate storage layer between the processor and main memory. The cache stores part of the data in main memory, which necessarily involves an address mapping. The simplest case is the **direct mapped** cache:

$$\text{block position in the cache}= \text{(block address)}\  \text{mod}\ \text{(number of blocks in the cache)}$$

There are also optimized mapping schemes:

- **Fully associative cache:** a cache organization in which a data block can be placed anywhere in the cache.
- **Set-associative cache**: a cache organization in which each data block has a fixed number of possible locations in the cache, at least 2. A set-associative cache where each block can be placed in n locations is called an n-way set-associative cache. Each data block can be placed in any of the n blocks within a set.

Because of this "one-to-many" relationship, an extra **tag** is also needed:

$$\text{(cache block position, tag)} \leftarrow \text{(block address)}$$

Assuming the data address is already known, the flow for accessing cache data is:

1. Obtain the cache block location (the index field) from the address.
2. Obtain the tag field from the remaining high bits of the address, to compare with the tag bits of the data stored in the cache.
3. Find the cache block that the index field points to. If the tag bits equal the tag field and the valid bit is set, it is a hit.
4. Otherwise, it is a miss.

If there is a cache miss, the following is needed:

1. Send the original value of the PC (program counter), that is, the current PC value minus 4, to memory, and stall the pipeline.
2. Perform a read on main memory and wait for main memory to complete the access.
3. Write into the cache: the data from main memory is written into the data part of the cache, the high bits of the address are written into the tag field, and the valid bit is updated to valid.
4. Restart instruction execution, that is, restart the instruction fetch.

The performance of cache reads and writes shows up mainly in the **number of cycles spent waiting for memory accesses**:

$$\text{cycles spent waiting on memory}=\frac{\text{instruction count}}{\text{program}}\times\frac{\text{miss count}}{\text{instruction count}}\times\text{read/write miss penalty}$$

Because the cache size is limited, cache misses are unavoidable, so software can also reduce the miss rate by improving temporal and spatial locality. Take matrix multiplication as an example:

$$A=BC \ \rightarrow \ a_{ij}=\sum_{k}b_{ik}\cdot c_{kj}$$

For a $(m\times k)(k \times n)$ matrix multiplication, the total number of multiplications is $mnk$, so in the worst case every piece of data is accessed from main memory, and the data volume is $2mnk$ (reads) $+\ mn$ (writes). But if the matrices $B$ and $C$ are tiled, that is, decomposed into $m/t\times k/t$ and $k/t\times n/t$ matrices, the original matrix multiplication can be converted into:

$$A_{ij}=\sum\limits_{l=1}^{k/t}B_{il}C{lj}$$

The volume of data read and written then becomes:

$$[2(mnk/t^3)+(mn/t)^2]*(t\times t)=2mnk/t+mn$$

### Multi-Level Cache Coherence

In a multi-core setting, each core has its own cache. If the single-core processor cache design is followed, the cores of a multi-core processor may see different values in their own caches.

This problem is called the **cache coherence** problem.

If a read of any data item returns the value most recently written to it, the memory system is said to be coherent. This leads to two concepts for correct shared memory:

- Coherence (cache coherence): what value a read returns
- Consistency (memory consistency): when a written value is returned by a read

A multi-core CPU has multiple L1 caches, so how can the data inside the caches be kept consistent so that system data does not become chaotic? This leads to a coherence protocol, `MESI`. `MESI` is formed from the initials of four states. Each cache line (the smallest storage unit of a cache) has 4 states, which can be represented with 2 bits. The following are the common state transitions and their triggering conditions:

| Current state           | State description                                                     | Operation             | State after transition     | Transition description                                                     |
| ------------------ | ------------------------------------------------------------ | ---------------- | -------------- | ------------------------------------------------------------ |
| **M** (Modified)  | The data in the current cache has been modified and is inconsistent with the copy in main memory.           | Another processor requests a read | **S** or **I** | After the data is written back to main memory, it is shared with the requesting processor (S), or the current cache state becomes invalid (I). |
| **E** (Exclusive) | The data in the current cache is the latest, consistent with main memory, and exists only in the current cache. | Own write | **M**          | The data is modified, and the state becomes Modified.                              |
| **E** (Exclusive) |                                                              | Another processor requests a read | **S**          | The data is shared, and the state becomes Shared.                              |
| **S** (shared)    | The data can exist in multiple caches and is consistent with main memory.                     | Own write | **M**          | When the data is modified, other caches are notified to invalidate it, and the state becomes Modified.            |
| **S** (shared)    |                                                              | Another processor requests a write | **I**          | When another processor wants to modify the data, the current cache is invalidated.                    |
| **I** (Invalid)   | The data in the current cache is invalid and cannot be used.                             | Own read | **E** or **S** | Depending on whether the data is shared, after loading the data the state is updated to Exclusive or Shared. |
| **I** (Invalid)   |                                                              | Own write | **M**          | After loading the data from main memory, it is modified directly, and the state becomes Modified.                |

Based on `MESI`, simulate data reads and writes on multiple cores. Suppose there are CPU A and CPU B, with their own cache a and cache b:

Read operations:

1. CPU A issues an instruction to read x from main memory.
2. CPU A reads x from main memory over the bus into cache a and sets that cache line to the E state.
3. CPU B issues an instruction to read x from main memory.
4. When CPU B tries to read x from main memory, CPU A detects an address conflict. CPU A then responds with the relevant data. Now x is stored in both cache a and cache b, and x is set to the S state (shared) in both cache a and cache b.

Modify operations:

1. After CPU A finishes its computation, it issues an instruction to modify x.
2. CPU A sets x to the M state (modified) and notifies CPU B, which has cached x.
3. CPU B sets x in its local cache b to the I state (invalid).
4. CPU A assigns the new value to x.

Synchronization after modification:

1. CPU B issues an instruction to read x.
2. CPU B notifies CPU A. When CPU A synchronizes the modified data to main memory, cache a is changed to E (exclusive).
3. CPU A synchronizes x to CPU B, and x in cache a and in the synchronized cache b is set to the S state (shared).

### Virtual Memory

Main memory acts as a "cache" for secondary storage such as disks and flash. This technique is called **virtual memory.**

The motivations for virtual memory:

- It allows memory to be shared efficiently and safely among multiple programs. Virtual memory translates a program's address space (a series of storage locations that only this program can access) into **physical addresses (addresses in main memory)**. This address translation strengthens the **protection (ensuring that multiple processes sharing the processor, memory, and I/O devices cannot read or write each other)** between the address spaces of the programs.
- It allows a single user program to use more memory than the memory capacity.

The CPU does not actually interact with physical memory addresses directly. Instead, a **memory management unit** (MMU) converts virtual addresses into actual physical addresses.

A virtual memory block is called a **page,** and a virtual memory miss is called a **page fault.**

In virtual memory, the processor produces a **virtual address**, which is translated by software and hardware into a physical address, and the physical address can then access main memory.

The process of mapping a virtual address to a physical address during a memory access is called **address translation.**

In virtual memory, an address is divided into a **virtual page number** and a **page offset.** The virtual page number can be translated into a physical page number, while the page offset stays the same in the physical address as in the virtual address.

## Storage Hardware

The storage hierarchy for LLMs ranges from fast, low-latency storage (such as registers and caches) down to high-capacity, low-cost storage (such as disks and network storage). It is mainly divided into the following levels:

| Level           | Storage type            | Characteristics                                           | Main use                                 |
| -------------- | ------------------- | ---------------------------------------------- | ---------------------------------------- |
| Registers         | Registers inside the processor    | Extremely fast, extremely small capacity                                 | Hold the operands needed by the instruction currently executing             |
| Cache (SRAM)     | L1/L2/L3 caches       | High-speed cache, small capacity                             | Temporarily hold frequently used data, reducing accesses to main memory       |
| High-speed storage       | HBM/GDDR memory       | High-bandwidth memory, DRAM designed and optimized for high bandwidth and low latency | Accelerate computation on the GPU and reduce memory bottlenecks          |
| Main storage (DRAM) | Dynamic random-access memory      | Large capacity, medium speed                               | Store model weights, activations, and intermediate results           |
| Disk storage       | SSD/HDD             | High capacity, slow                                 | Store rarely used weights, model snapshots, and pretraining datasets |
| Distributed storage     | NVMe over Fabric, etc. | Very large capacity, high latency                             | Weight loading and storage in a distributed environment             |

The GPU storage hierarchy can usually be divided into the following levels, from the fastest but smallest registers to the slowest but largest global memory and host memory:

| Storage level             | Location                     | Characteristics                                  | Use                                         |
| -------------------- | ------------------------ | ------------------------------------- | -------------------------------------------- |
| Registers               | Private to each CUDA core       | Fastest, smallest capacity                        | Hold a thread's local variables, for frequently accessed data       |
| Shared memory             | Shared by all threads of a thread block | Fast, low latency, limited capacity (48 KB~64 KB) | Share data among threads and reduce global memory accesses             |
| L1 cache              | Private to each SM             | High-speed cache, low latency, small capacity            | Cache frequently accessed data from local memory or global memory       |
| L2 cache              | Shared by all SMs             | Larger capacity (a few MB), higher latency           | Cache global memory data and optimize data access across SMs   |
| Global memory             | DRAM on the GPU device        | High bandwidth, large capacity (16 GB~80 GB)         | Store large-scale data, such as model weights, inputs, and intermediate results |
| Texture/constant memory        | Dedicated memory regions             | High bandwidth, supports read-only optimization                  | Used to access read-only data, such as textures or constants             |
| Host memory (CPU memory) | Host system memory             | Very large capacity, high latency                              | Store data that exceeds GPU memory, loaded or swapped dynamically      |
